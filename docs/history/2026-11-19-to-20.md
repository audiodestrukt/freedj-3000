## 2. The CDJ1 stick and "things not reading"

Dan asked to convert his stick to "rekordbox 7 format" because testers
reported things not reading.  The stick already was a rekordbox 6/7
export:
- `export.pdb` plus `exportLibrary.db`;
- 227 tracks, each with all three analysis files (`.DAT`, `.EXT`, `.2EX`).

It had cues on only 1 track.  Its Nov 18 changes were made by rekordbox
running under Wine on this box (it was still running and holding the LINK
ports).  The reports turned out to be about cues (section 3).

## 3. Cues: a CDJ got an empty list for most tracks

`2d3c606`.  OpenDeck's dbserver served cues only for the track loaded on
its own deck.  Every other library track answered an empty cue list,
because the media server's scan never read the stick's ANLZ cues.  The
scan now reads every rekordbox export at the served folder or one level
down.

It slipped because the only serving test fed the server cues by hand.  New
end-to-end test: a stick with cues set in rekordbox is scanned and served,
then asked for a track's cue list exactly as a CDJ asks.  Without the fix
it gets `[]`.

Still open: cues set on OpenDeck itself for tracks other than the loaded
one aren't saved (#65).

## 4. "Linked to player with older firmware"

`4bb0069`.  Dan's testers' CDJ-3000s showed this message.  OpenDeck's
keep-alive carried an XDJ-1000MK2's bytes at `0x21` / `0x35`; a CDJ-3000
sends `0x03` / `0x64`.  It was found by capturing one announce packet from
an emulated unit and diffing it against ours.  A test pins the announce to
the capture.  The status packet's firmware string is not what triggers it.

## 5. The stacked waveform: OpenDeck as master

Fixed: status byte `0xcd` must be `0xf3`, not the XDJ's `0x03`.  The full
story is in
[`../bugfixes/cdj3000-stacked-waveform-status-byte.md`](../bugfixes/cdj3000-stacked-waveform-status-byte.md).

What was learned about the CDJ-3000's WAVEFORM view:
- It fetches the master's stored analysis (PWV7, PWV5, detail, grid, PQT2,
  cues) over dbserver once, when the master loads a track or a new master
  starts playing, and draws it locally from the position packets.
- Tapping the meter requests nothing.
- A watching unit doesn't need a track of its own.

What was ruled out on the way:
- serving a real rekordbox `export.pdb` (the CDJs never open it);
- the model name;
- the firmware string;
- status byte `0x9d`;
- load order;
- which unit watches;
- NFS.

The rekordbox-as-oracle route (rekordbox in a network namespace on
`djlink0`) was set up but not needed.

Two tests guard it:
- `cdj3000_status_lets_peers_fetch_our_waveform` checks the byte.
- `cdj3000_status_matches_a_captured_master_byte_for_byte` compares the
  whole status with a captured master's. It lists the 18 known differences
  with reasons and fails on any new one.

Method notes for next time:
- Diff against a real player in the same role first.
- Run controls inside one OpenDeck session.
- Restart the emulated units' firmware (`restart` on the control API) when
  their behaviour drifts.

## 6. Answers along the way

- **Does a CDJ-3000 take master on its own?**  Yes.  With no master on the
  network, a unit that starts playing takes master (seen on the emulator),
  as Dan's tester said.  OpenDeck takes master only when asked (MASTER), or
  when it's synced and the master has gone silent.  Matching the CDJ is
  still open.
- **Stacked waveform both ways:** CDJ → OpenDeck is PR #54 (tested on a
  real CDJ-3000, not merged yet).  OpenDeck → CDJ is this fix.
- **rekordbox stems:** rekordbox splits stems in Performance mode (paid
  plan); stock CDJ-3000s can't play them.
- **rekordbox under Wine on `djlink0`:** it has no network-adapter setting;
  it uses the default route (the LAN).  It holds the LINK ports and
  dbserver port 12523 while its agent runs (`wineserver -k` frees them).
- The XDJ-1000MK2 service manual was Taildropped to Dan's MacBook Air
  (never committed).
